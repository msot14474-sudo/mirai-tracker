# M08 — Planned-date calculation engine

M08 converts the ordered M07 lesson plan into expected start and finish dates using the dated teaching sessions generated by M06. It keeps the calculation explainable: every topic consumes a known number of minutes from real classes, in order, and every saved result has a version and reason.

## Calculation rule

The engine sorts topics by unit sequence and then topic sequence. It sorts sessions by start time. It fills each topic from the available session minutes until that topic is complete, then gives any minutes left in the same session to the next topic.

Only `SCHEDULED`, `IN_PROGRESS` and `COMPLETED` sessions provide capacity. `CANCELLED`, `SKIPPED` and `MERGED` sessions are excluded. M04 holidays are already absent because M06 does not generate teaching sessions on non-working dates.

For every fully allocated topic, the engine returns:

- the first session date as `plannedStartDate`;
- the last session date as `plannedFinishDate`;
- the allocated minutes and contributing session IDs;
- whether the finish date is after the offering target.

If the timetable ends during a topic, that topic reports its allocated and remaining minutes. Later topics remain unscheduled. The summary exposes required, available, allocated and shortfall minutes so insufficient capacity cannot look like a successful plan.

## Hand-worked example

Three topics require 90, 120 and 60 minutes. Five one-hour classes are available on 1, 3, 8, 10 and 15 July.

| Topic | Required | Normal start | Normal finish | After 3 July is cancelled   |
| ----- | -------- | ------------ | ------------- | --------------------------- |
| A     | 90 min   | 1 July       | 3 July        | 1–8 July                    |
| B     | 120 min  | 3 July       | 10 July       | 8–15 July                   |
| C     | 60 min   | 10 July      | 15 July       | 30 min placed, 30 min short |

Removing 3 July leaves 240 minutes for 270 minutes of syllabus. Topic A shifts to 8 July, topic B shifts to 15 July and topic C exposes a 30-minute shortfall. An M04 holiday has the same effect because its session never enters the calculation.

## Versioning and cancellation

`POST /topic-schedules/offerings/:offeringId/calculate` saves the next `TopicScheduleVersion`. The first run uses `INITIAL` unless the caller supplies a reason; later manual runs use `MANUAL_RECALCULATION`. Each version stores only complete topic allocations, while the response also reports partial and unscheduled topics.

`PATCH /topic-schedules/sessions/:sessionId` cancels or restores an unlogged scheduled class. Cancellation requires a reason. Logged, completed, in-progress, skipped and merged sessions are protected. A successful cancellation immediately saves a new version with `SESSION_CANCELLED`; restoring the class saves `MANUAL_RECALCULATION`. Both the class change and calculation are audited.

Historical schedule versions remain available for later progress and reporting features. A version never overwrites an earlier calculation.

## Access

- Admin and Program Manager users can calculate every offering.
- Campus Manager users can calculate offerings in their assigned campuses.
- Faculty users can calculate only their active assigned offerings.
- Students cannot open or mutate the M08 workspace.

Every route enforces the same offering policy in the API. The interface hides the workspace by role for clarity.

## API

| Method  | Route                                              | Purpose                                                        |
| ------- | -------------------------------------------------- | -------------------------------------------------------------- |
| `GET`   | `/topic-schedules/offerings`                       | List accessible offerings with plan/session/version summaries  |
| `GET`   | `/topic-schedules/offerings/:offeringId`           | Return the live calculation, sessions and latest saved version |
| `POST`  | `/topic-schedules/offerings/:offeringId/calculate` | Persist the next version and complete topic entries            |
| `PATCH` | `/topic-schedules/sessions/:sessionId`             | Cancel or restore an unlogged class and recalculate            |

The detail route prefers the active lesson plan. If no active plan exists yet, it uses the newest draft so faculty can inspect dates before activation.

## Verification

Unit tests cover minute carry-forward, topics spanning multiple classes, input ordering, included/excluded session states, invalid durations, holiday removal, cancellation shifts and shortfalls. Service tests cover faculty scope, active-plan preference, version persistence, audit writes, automatic cancellation recalculation, logged-session protection and missing plans. React tests cover the timeline, shortfall, version save and cancellation payload.

The PostgreSQL suite checks that allocated minutes are positive and that a topic can appear only once in one schedule version. Run it after a migrated PostgreSQL instance is available:

```bash
pnpm db:test
```
